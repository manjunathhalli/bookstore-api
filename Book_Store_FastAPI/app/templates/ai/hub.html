Behind the scenes

These features have no page — they run on their own. When you submit a review it is screened for abuse/spam and rated positive, neutral or negative; when an admin saves a book it is auto-tagged by genre and indexed for semantic search; and admins can generate a description from the add-book form.

🧩 How this all works

Six building blocks, in the order they stack on top of each other. Each one below links to the feature on this page that actually uses it, with the real file/function so you can go read the code.

🔢 1. Embeddings

Text → a vector of numbers

An embedding model turns text into a fixed-length list of floats (384 numbers here) such that texts with similar meaning end up as nearby vectors — even if they don't share a single keyword ("space adventure" lands close to "sci-fi voyage story"). This app runs the all-MiniLM-L6-v2 model locally (via fastembed/ONNX, falling back to sentence-transformers) — no API key, no network call.

Used by: Semantic Search (book → vector, stored in the DB) and the Business Central Chatbot (each BC record → vector, stored in Qdrant).

# app/core/ai.py — ClaudeService.embed()
vector = model.embed(["Dune by Frank Herbert: a desert planet..."])
# -> [0.0123, -0.081, 0.044, ...]  (384 numbers, unit-length)
⬇

🗄️ 2. Vector DB

Store vectors, search by "closest meaning"

A vector database stores those embeddings and can answer "which stored vectors are closest to this vector?" almost instantly, even over millions of rows — the same job a normal index does for exact matches, but for similarity. This app uses two approaches on purpose, to show both ends of the spectrum:

  • Semantic Search — book embeddings live in a plain MySQL column; similarity is computed in Python with cosine distance (fine at catalogue scale, zero extra infra).
  • Business Central Chatbot — BC record embeddings go into Qdrant (app/bc/), a real vector database, run embedded (a local folder, ./qdrant_storage) so it needs no server either.
# app/ai/service.py — cosine(), semantic_search()
score = cosine(query_vector, book.embedding)   # -1..1, higher = more similar

# app/bc/ — Qdrant client, same idea at scale
qdrant.search(collection_name="business_central", query_vector=vector, limit=8)
⬇

📚 3. RAG (Retrieval-Augmented Generation)

Retrieve real data, then ask the LLM to answer only from it

An LLM only knows what was in its training data — it has never seen this store's books or your orders. RAG fixes that in two steps: retrieve the relevant rows (by keyword match, or by the embedding similarity above), then paste them into the prompt as grounding context, with an instruction to answer using only that context. The model reasons over real rows instead of guessing — it can't invent a book that isn't in the catalogue.

Used by: AI Chatbot (RAG) and the Business Central Chatbot.

# app/ai/service.py — rag_chat_reply()
catalog = "\n".join(f"- {b.name} by {b.author} (Rs.{b.price})" for b in matching_books)
system = f"Answer using ONLY the CATALOG below.\nCATALOG:\n{catalog}"
claude.ask(user_message, system)
⬇

🔗 4. LangChain

A library for wiring LLMs + tools + prompts together

LangChain is a Python framework that standardises the pieces above so you don't hand-roll them: a common interface for any LLM provider (ChatGroq, ChatAnthropic, ChatOllama — swap providers with one line), prompt templates, and — the important part for an agent — a way to describe Python functions as tools the model can choose to call.

Used by: AI Chatbot (Agent) — app/ai/agent.py.

# app/ai/agent.py — _make_llm() picks the provider from settings.ai_provider
if settings.ai_provider == "ollama":
    llm = ChatOllama(base_url=settings.ollama_base_url, model="qwen2.5")
elif settings.ai_provider == "groq":
    llm = ChatGroq(api_key=settings.groq_api_key, model=settings.groq_model)
⬇

🕸️ 5. LangGraph

LangChain's tool-calling loop, made into an explicit graph

LangChain's basic agent loop is a fixed cycle: ask the model → it picks a tool → run the tool → feed the result back → repeat. That's what the plain Agent chatbot does. LangGraph is a companion library that draws that loop as an explicit graph of nodes and edges instead — so it can branch. This app uses it for exactly the branch a fixed loop can't express: a big order needs a human "yes" before it's placed.

Used by: AI Chatbot (LangGraph) — app/ai/graph_agent.py.

# app/ai/graph_agent.py — the graph
graph.add_node("agent", call_model)     # LLM decides: reply, or call a tool
graph.add_node("tools", ToolNode(tools))  # run search_catalog / my_orders / add_to_cart
graph.add_node("confirm", confirm_node)   # place_order over Rs.2,000 lands HERE instead
graph.add_conditional_edges("agent", route, {"tools": "tools", "confirm": "confirm", END: END})
graph.add_edge("tools", "agent")          # tool results go back to the model
graph.add_edge("confirm", END)            # ...and confirm ends the turn, awaiting "yes"/"no"

# Next message: "yes" -> the order is actually placed; "no" -> cancelled.
# The plain AgentExecutor loop (Feature 5a) has no node to pause at — it would
# just place the order immediately. That's the concrete win LangGraph buys here.
⬇

🤖 6. AI Agents

The LLM decides which action to take, not just what to say

Put it all together and you get an agent: an LLM given a goal (the user's message) and a set of tools, that decides for itself which tool(s) to call, in what order, and when it has enough information to answer — instead of a developer hand-coding "if the message contains 'weather', call the weather API." The safety model doesn't change: the model never sees SQL or raw data access, only typed Python functions that run parameterised queries scoped to the signed-in user. This app has two agents over the identical tool set — a plain LangChain loop, and the LangGraph graph above that adds the order-confirmation branch.

Try it: ask either chatbot "what's the weather in Mysuru and recommend a thriller under 500" — then ask the LangGraph one to order 5 copies of something over Rs.2,000 and watch it pause for confirmation.

# app/ai/agent.py — the tools both agents choose between
[weather, search_catalog, my_orders, add_to_cart, place_order]
# The LLM reads your message, picks zero or more of these, and only THEN replies.
⬇

🎛️ 7. Fine-Tuning

Don't re-supply knowledge every request — bake it into the model instead

Everything above hands the model fresh instructions or data on every single call — a system prompt, retrieved rows, or a tool result. Fine-tuning is the different move: keep training a pretrained representation — just a small classifier head, here — on labelled examples from this specific business, so the knowledge lives in the model's weights instead. The trained model then answers instantly: no prompt, no retrieval, no LLM API call at all.

Used by: Fine-Tuning (admin) — trains a classifier on this store's own reviews, labelled by what customers actually rated (4-5 ⭐ = Positive, 3 ⭐ = Neutral, 1-2 ⭐ = Negative), not by the zero-shot LLM's own guess in Sentiment Analysis — so the side-by-side comparison it shows is honest. Trade-off vs. RAG: cheap/instant inference and no context to resend, but it needs labelled data up front and stays static until retrained (RAG updates the moment you add a row to the database). 

# app/ai/finetune.py — train()
vectors = claude.embed_many(review_texts)          # same local embeddings as Semantic Search
clf = LogisticRegression().fit(vectors, ratings_as_labels)
joblib.dump(clf, "sentiment_finetuned.joblib")     # saved once, reused for every future prediction

# app/ai/finetune.py — predict() — no LLM call, no network, just this store's model
clf.predict([claude.embed(new_review_text)])

🎭 Generative AI vs. Agentic AI vs. AI Agent

Three terms people use almost interchangeably, but they describe different layers — one builds on the next. Every example below is a real feature on this page, not a hypothetical.

🧬 Generative AI A model that turns a prompt into new content — text in, text (or JSON) out. One call, no memory, no tools. No — it only describes, never does. Book Description Generator, Review Summarization, Auto-Tagging, Demand Forecasting, AI Chatbot (RAG)
🤖 AI Agent Generative AI + a set of callable tools + a loop: the model decides which tool(s) to call, runs them, and reasons over the result before replying. Yes — within the tools it's given. 🧬 Generative AI

Prompt in → content out. No tools, no actions, no memory.

This is the layer everything else is built on: one call to an LLM that generates text or structured JSON from a prompt, and stops. It doesn't know what a "cart" is and can't check anything live — it only writes. Six separate features on this page are exactly this, nothing more:

  • Book Description Generator (admin, add-book form) — writes 40–60 words of marketing copy from a title + author.
  • Review Summarization — condenses up to 50 reviews into a balanced 2–3 sentence summary.
  • Auto-Tagging — writes 1–4 genre tags for a new book.
  • Demand Forecasting — writes a trend + reason per book from real order counts.
  • Sentiment / Moderation — classifies a review as Positive/Neutral/Negative, or Safe/Unsafe.
  • AI Chatbot (RAG) — writes an answer from retrieved context; it can talk about your orders, but can't touch them.
# app/ai/service.py — generate_description() — the shape of every one of these
claude.ask(
    f'Write a description for "{name}" by {author}.',
    system="You are a bookstore copywriter. 40-60 words. No headings.",
)
# -> one string back. No tool was available to call; there was nothing TO call.
⬇

🤖 AI Agent

Generative AI + tools + a decide-then-act loop

Give that same generative model a list of Python functions it's allowed to call ("tools"), and a loop that feeds tool results back to it, and it stops being a text generator and becomes an agent: something that can actually search the catalogue, look up your real orders, add a book to your cart, or place an order — not just describe doing so.

Both chatbots on this page are AI Agents over the identical tool set — they only differ in how the loop is wired (see LangChain vs. LangGraph above).

# app/ai/agent.py — what makes it an AGENT, not just generative AI
tools = [weather, search_catalog, my_orders, add_to_cart, place_order]
executor = AgentExecutor(agent=create_tool_calling_agent(llm, tools, prompt), tools=tools)
executor.invoke({"input": "add Clean Code to my cart"})
# -> the model picks add_to_cart, it actually runs, THEN the model replies.
# Compare to generative AI above: there, "add it to my cart" would just get
# talked about. Here, it happens.
⬇

🕸️ Agentic AI

The system, not the model — branching, memory, and pausing for approval

"Agentic AI" is the broader claim: not just that a model can call a tool, but that the whole application is designed around autonomous, multi-step decision-making — with state that persists across turns, branches that change the path based on what happened, and (when the stakes are high enough) a deliberate pause for a human. A single AI Agent call is one decision; an agentic system is a sequence of them with memory in between. This page's clearest example is the LangGraph chatbot's own conversation, captured live:

  1. You: "Order 5 copies of The Midnight Library" → the agent adds it to your cart and asks if you want to check out.
  2. You: "yes" → using its short memory of turn 1, it now calls place_order for ₹6,995 — over the ₹2,000 threshold, so the graph branches to the confirm node instead of buying immediately, and asks you to actually confirm.
  3. You: "yes" again → this time no LLM call happens at all — the pending order is resolved directly — and the order is placed (or, as in testing, it correctly reports "you have no saved address yet" instead of crashing).

That's agentic: the same words ("yes") did two completely different things depending on state the system remembered — a plain one-shot generative call could never do that.

# app/ai/graph_agent.py — the state that makes it "agentic", not just "an agent"
_pending: dict[int, dict] = {}   # order awaiting a human "yes"/"no", per user
_history: dict[int, list] = {}  # short conversation memory, per user

if lower in _CONFIRM_WORDS:       # "yes" resolves a PENDING order directly —
    place_order.invoke(pending)   # no LLM call needed, the decision already happened
